# Project Summary: BlueRetro — подключение 2х NES/Dendy джойстиков к Murmulator

## Связанные документы
- **Базовый проект**: [BlueRetro](https://github.com/darthcloud/BlueRetro) (darthcloud) — open-source адаптер Bluetooth-контроллеров для ретро-консолей на базе ESP32, на чьих прошивке и HW1-спецификации построена данная сборка. Документация: [BlueRetro Wiki](https://github.com/darthcloud/BlueRetro/wiki).
- **Связанный проект-хост**: `murmulator-vga-project-summary.md` (проект "Murmulator") — одна из сборок Мурмулятора (RP2040 Black Perfboard: VGA, Joystick, AudioOut, AudioIn), используемая для текущей интеграции BlueRetro; не единственная возможная целевая платформа. Файл загружается отдельно в Project Knowledge.

## Цель проекта
Подключить Bluetooth-геймпады (Xbox One, PS/Switch и др. HID-устройства) к Murmulator (устройство на базе RP2040) в качестве двух NES/Dendy-совместимых джойстиков через устройство BlueRetro, которое эмулирует стандартный протокол сдвигового регистра NES/Dendy (9-pin, CLOCK/LATCH/DATA) на выходе, выступая мостом между Bluetooth-контроллерами и Мурмулятором. Физические проводные NES/Dendy-джойстики в проекте не используются.

## Контекст компонентов

### Murmulator (эмулятор ретро компьютеров)
- Основа: RP2040 black clone, самодельная плата (Perfboard).
- Функциональность (согласно `murmulator-vga-project-summary.md`): вывод VGA, поддержка джойстика, аудиовыход, аудиовход.
- Данный проект расширяет базовую платформу поддержкой двух NES/Dendy джойстиков через BlueRetro.

### BlueRetro (адаптер)
- Открытое железо и прошивка на базе ESP32, лицензии CERN-OHL-P-2.0 (hardware) и Apache-2.0 (software).
- Изначально спроектирован как переходник "Bluetooth-контроллер → консоль": <cite index="5-1">поддерживает Wii, Switch, PS3, PS4, PS5, Xbox One, Xbox Series X|S и generic HID Bluetooth (BR/EDR и LE) устройства, а на выходе эмулирует протоколы множества консолей, включая NES</cite>.
- Для NES/Famicom: <cite index="2-1">может эмулировать стандартный 8-кнопочный NES-контроллер (GamePad), мультитап Four Score на 4 контроллера (Dual), японский 4P-адаптер (Alt), клавиатуру Famicom или Hori Trackball (мышь)</cite>.
- В данном проекте используется **штатный** сценарий работы BlueRetro: адаптер физически подключается к джойстик-порту хоста (в данном случае — к Murmulator) и эмулирует на выходе стандартный NES/Dendy-протокол сдвигового регистра, а на вход принимает Bluetooth/HID-геймпады (Xbox One и др.). Проводные NES/Dendy-джойстики на входе BlueRetro не используются.
- Схемы распайки NES-кабелей и особенности PAL-подтяжек описаны в [BlueRetro Cables Build Instructions](https://github.com/darthcloud/BlueRetro/wiki/BlueRetro-Cables-Build-Instructions): <cite index="4-1">для PAL-систем требуется добавление подтягивающих резисторов 3.6К к NES 5V (pin 5) на пады IO18, IO5 и IO32</cite>.
- Общая сборка описана в [BlueRetro DIY Build Instructions](https://github.com/darthcloud/BlueRetro/wiki/BlueRetro-DIY-Build-Instructions): прошивка BlueRetro на ESP32, сборка кабеля-адаптера под целевую систему, опциональная настройка через Web Bluetooth.
- **В данном проекте**: на плате BlueRetro распаяны 2 разъёма JST XH 1x04 (J1/J2), к которым подключены самодельные кабели-переходники JST XH 4-pin male → DE-9 female, оканчивающиеся разъёмами DE-9 female — они подключаются напрямую к джойстик-портам DE-9 male на Murmulator.
- Настройка выполняется через BLE Web Config (Desktop/Android Chrome), позволяющий гибко маппить кнопки, настраивать turbo-режимы и т.д.

## Выбор Dev Board (ESP32)

**Итоговое решение: ESP32 D1 mini MH-ET LIVE (CH9102).**

**Рассмотренные альтернативы:**

| Плата | Вердикт |
|---|---|
| ESP32-WROOM-32 DevKit, **30 pin**, CP2102 | Отпала — на этом форм-факторе физически **не выведен пин GPIO0**, необходимый для BOOT/pairing и всех режимов сброса BlueRetro (проверено по пинаутам конкретных плат в наличии) |
| ESP32-WROOM-32 DevKit, **38 pin**, CP2102 | Технически пригодна и соответствует официальной рекомендации автора BlueRetro (см. ниже) — GPIO0 выведен. Не выбрана, так как потребовала бы переделки уже готовой и проверенной в железе KiCad-схемы (другой footprint, другие габариты платы); на текущем этапе (PCB близка к финализации) это признано нецелесообразным |
| ESP32 D1 mini MH-ET LIVE, CH9102 (выбрана) | Схема и распиновка уже спроектированы и проверены в железе под эту плату; конфликтов бортовой периферии с используемыми пинами (IO2, IO4, IO5, IO17, IO18, IO19, IO22, IO32, IO0) не выявлено |

**On-board LED платы:** на ESP32 D1 mini MH-ET LIVE штатный (built-in) LED подключён к **GPIO2** и загорается, когда GPIO2 находится в состоянии **HIGH**. В данной сборке GPIO2 занят под индикацию порта 1 (см. раздел «LED-подсистема индикации» ниже) — при HIGH на IO2 (LED порта 1 через MOSFET Q1 горит) штатный on-board LED платы будет параллельно повторять это состояние (гореть одновременно с внешним LED порта 1). Это не создаёт электрического конфликта (GPIO2 остаётся выходом, on-board LED — лишь дополнительная, немного избыточная индикация того же сигнала), но стоит иметь в виду при сборке в корпусе — штатный LED платы может быть виден снаружи, если не закрыт.

**Официальная позиция сообщества BlueRetro:** автор проекта (darthcloud) в официальной документации указывает конкретную рекомендуемую плату — **ESP32-DevKitC-32E/D с модулем ESP-WROOM-32** (38-pin форм-фактор). Причины:
- На дешёвых клонах бывают конфликты бортовой периферии с пинами, которые использует BlueRetro (задокументированный случай — светодиод на IO5 на плате Wemos Lolin32, из-за которого прошивка зависает в цикле сброса).
- Важно, чтобы внутри стоял модуль именно **WROOM** (не WROVER) — у WROVER на 2 GPIO меньше из-за встроенной PSRAM.
- Сторонние производители готовых китов для BlueRetro (например, RetroRosetta) придерживаются той же рекомендации — использовать только официальные DevKit-платы.

**Почему аргумент «штатная кнопка BOOT» не сыграл роли:** кнопки BOOT и RESET в данном проекте в любом случае выносятся на корпус устройства (3D-печатной коробки) отдельными проводами — поэтому наличие или отсутствие штатной кнопки BOOT на самой плате не имеет значения при выборе.

**Известный компромисс выбранной платы — нагрев регулятора:** встроенный линейный стабилизатор **AMS1117** (5V→3.3V) на D1 mini греется в работе до ~54°C. Это не уникальная проблема D1 mini — тот же AMS1117 стоит и на WROOM-32 DevKit платах, но на маленькой плате D1 mini меньше меди PCB для отвода тепла. 54°C не критично для самого регулятора, но близко к температуре размягчения PLA (используется в 3D-печатном корпусе) — при плотной компоновке возможна деформация пластика при долгой работе без вентиляции.

⚠️ **Решение по нагреву сознательно отложено** (риск принят, вопрос не блокирует сборку). При необходимости в будущем — два варианта:
1. Вентиляционное отверстие в корпусе над регулятором.
2. Обход/выпайка встроенного AMS1117 с подачей готовых 3.3V от отдельного внешнего DC-DC регулятора (по аналогии с доработкой SD-модуля в `murmulator-vga-project-summary.md`, раздел 2).

## Аппаратная сборка BlueRetro
- Используется DIY-сборка на базе **ESP32 D1 mini (MH-ET LIVE, USB-serial чип CH9102)** — самодельная, не готовая плата BlueRetroHW.
- **⚠️ Кнопка BOOT/IO0 отсутствует на плате D1 mini.** В отличие от полноразмерного ESP32 DevKitC, на D1 mini физически разведена только кнопка **RST/EN** (сброс модуля) — отдельной кнопки BOOT нет. Функции BlueRetro (пейринг, сброс конфигурации, factory reset — см. раздел "Кнопка BOOT (IO0)" ниже) завязаны именно на IO0, поэтому нужно **допаять отдельную кнопку между IO0 и GND**.
  - Внешний pull-up резистор в теории не обязателен — ESP32 включает внутренний pull-up на IO0 (strapping-пин) аппаратно при старте. Кнопка просто замыкает IO0 на GND при нажатии.
  - **На практике встроенный pull-up на конкретном модуле оказался нестабильным** (см. раздел «LED-подсистема» — известный глюк с самопроизвольным срабатыванием 6–10 сек сброса), поэтому в финальной KiCad-схеме внешний резистор **R1 = 10 кОм (от IO0 к +3.3V) впаян безусловно**, как штатный компонент, а не как опциональный запасной вариант.

### Кнопка BOOT (IO0) — функции BlueRetro
⚠️ Тайминги и действия ниже соответствуют используемой версии прошивки (`v25.04_hw1`, см. раздел "Прошивка firmware"). В других версиях BlueRetro длительности удержания и результат могут отличаться — сверяться с BlueRetro Wiki для конкретной установленной версии.
- Короткое нажатие (< 3 сек) — обычный сброс системы.
- Удержание 3–6 сек (LED IO17 мигает медленно) — запуск режима пейринга (pairing mode).
- Удержание 6–10 сек (LED IO17 мигает быстро) — сброс к дефолтной конфигурации.
- Удержание > 30 сек — полный factory reset ESP32 (заводская прошивка + сброс настроек).
- В режиме пейринга короткое нажатие останавливает пейринг / отключает все Bluetooth-устройства.

## Распиновка (согласовано с murmulator-vga-project-summary.md)

**Топология:** ESP32 (BlueRetro) → разъёмы J1/J2 (JST XH 1x04, на плате BlueRetro) → кабель-переходник (JST XH 4-pin male → DE-9 female) → разъёмы J6/J7 (DE-9 male, на плате Murmulator) → GPIO Pico.

| Сигнал | Нога ESP32 (BlueRetro) | JST XH J1 (P1) | JST XH J2 (P2) | DE-9 Murmulator J6 (P1) | DE-9 Murmulator J7 (P2) | GPIO Pico |
|---|---|---|---|---|---|---|
| LATCH (общий) | IO32 | pin 1 | pin 1 | pin 3 | pin 3 | GP15 |
| CLOCK порт 1 | IO5 | pin 2 | — | pin 4 | — | GP14 |
| CLOCK порт 2 | IO18 | — | pin 2 | — | pin 4 | GP14* |
| DATA порт 1 | IO19 | pin 3 | — | pin 2 | — | GP16 |
| DATA порт 2 | IO22 | — | pin 3 | — | pin 2 | GP17 |
| GND | GND ESP32 | pin 4 | pin 4 | pin 8 | pin 8 | GND |
| VCC (+5V) | — | не разведено | не разведено | pin 6 | pin 6 | **не подключать** |

**Распайка кабеля-переходника (JST XH 4-pin male → DE-9 female), одинаковая для обоих портов:**

| JST XH pin | Сигнал | DE-9 pin |
|---|---|---|
| 1 | LATCH | 3 |
| 2 | CLOCK | 4 |
| 3 | DATA | 2 |
| 4 | GND | 8 |

\* **CLOCK и LATCH генерирует RP2040 (Murmulator выступает хостом/консолью)** — это один физический сигнал GP14/GP15, разведённый на оба разъёма J6 и J7 одновременно. IO5 и IO18 на ESP32 (BlueRetro эмулирует джойстик/слейв) — это два **входа**, слушающие этот сигнал, а не два независимых генератора. Электрического конфликта (bus contention) при объединении не возникает, так как RP2040 — единственный активный драйвер линии. Прошивка BlueRetro внутренне обрабатывает IO5/IO18 как два независимых входа CLOCK (на случай консолей, где CLOCK P1/P2 физически не объединены) — при подключении к Murmulator оба входа неизбежно получают один и тот же физический сигнал. Проверка осциллографом перед пайкой всё равно рекомендуется — не для сравнения "двух генераторов", а чтобы убедиться, что сигнал доходит до обоих входов ESP32 чисто, без искажений на проводах/разъёмах.

VCC (pin 6, DE-9 Murmulator) сознательно не подключается: ESP32 внутри BlueRetro работает на 3.3V-логике, сигнальные линии заводятся на GPIO Pico напрямую без level-shifter'ов; питание BlueRetro организовано отдельно, через собственный разъём J3 платы (см. раздел "Питание BlueRetro"). На разъёмах JST XH J1/J2 (порты джойстика на стороне BlueRetro) линии +5V нет вообще — там только 4 сигнала (LATCH/CLOCK/DATA/GND).

## Питание BlueRetro (ESP32-модуль)
- ESP32-модуль (DevKit со встроенным стабилизатором AMS1117, 5V→3.3V) запитывается отдельным проводом от шины **5V внешнего PSU** Murmulator (не от Vout/USB) — на YD-RP2040 нет доступного "чистого" USB VBUS до объединяющего диода BAT54C, поэтому 5V от USB для ESP32 недоступны.
- **⚠️ Ограничение (при питании через шину 5V PSU):** BlueRetro и оба джойстика работают только при подключённом внешнем PSU к Murmulator — при питании платы только от USB Murmulator (без внешнего PSU) джойстики работать не будут. Это ограничение не действует при альтернативном варианте питания ESP32 через его собственный USB-порт (см. ниже).
- **Измерено (мультиметр):** пиковое потребление тока ESP32-модуля по шине 5V при активном BT-радио — **~155 мА**. Так как ESP32 запитан отдельным проводом напрямую от шины PSU (в обход диода BAT54C и узла Vout, см. `murmulator-vga-project-summary.md`), эта нагрузка не делит бюджет тока с PS/2-клавиатурой и не ограничена номиналом BAT54C (~150–300 мА на плечо) — запас по току достаточен.
- **Альтернативный вариант питания:** возможно запитать BlueRetro через собственный USB-порт на ESP32-модуле (micro-USB на плате D1 mini) вместо шины 5V PSU Murmulator. GND сигнальных линий (LATCH/CLOCK/DATA) остаётся общим с Мурмулятором в любом случае — через разъёмы J1/J2 (JST XH) и кабель-переходник к J6/J7, независимо от источника 5V для самого модуля. При этом варианте ограничение выше (обязательный внешний PSU у Мурмулятора) снимается — питание ESP32/BlueRetro не зависит от того, подключён ли PSU к Мурмулятору.

## Входная защита питания, RESET и развязка

**Разъём внешнего 5V (J3) и защитный диод D1:**
- **J3** — отдельный 2-контактный разъём («External 5V Power Connector»), через который на плату заводится питание от шины 5V внешнего PSU (см. раздел «Питание BlueRetro» выше).
- **D1 = 1N5819** (Schottky, 40V/1A) включён между J3 и шиной +5V: анод — со стороны J3, катод — со стороны +5V. Функция — защита от переполюсовки / развязка входа (аналог diode-OR BAT54C на самом Мурмуляторе, см. `murmulator-vga-project-summary.md`, раздел 10).

**Кнопка RESET (SW2):**
- Отдельная кнопка **SW2**, замыкающая **RST** ESP32-модуля на GND — штатный аппаратный сброс модуля, независимый от логики BOOT/IO0 (см. таблицу функций кнопки BOOT выше).

**Развязывающие конденсаторы (bulk + bypass на обеих шинах питания):**

| Шина | Bulk (электролит) | Bypass (керамика) |
|---|---|---|
| +5V (вход, после J3/D1) | C5 = 470 мкФ | C6 = 100 нФ |
| +3V3 (выход стабилизатора ESP32-модуля) | C8 = 220 мкФ | C7 = 100 нФ |

Оба конденсатора на каждой шине включены параллельно, между шиной и GND — классическая пара «объёмная фильтрация + высокочастотная развязка».

## LED-подсистема индикации (финальная, проверено в железе)

По документации BlueRetro Wiki (разделы про LED usage) индикация состоит из двух типов светодиодов: **один global-status LED на IO17** и до **четырёх port-status LED** (по одному на порт). В данной сборке реализованы global-LED + два port-LED (на оба порта джойстика, P1/P2).

**Примечание про IO17 vs встроенный LED платы:** на некоторых ESP32 DevKitC/D1 mini платах штатный (built-in) LED сидит на IO2, но в прошивке BlueRetro этот вывод занят под цепь авто-программирования — поэтому для индикации нужен отдельный внешний светодиод именно на IO17, не полагаясь на встроенный power/status LED платы.

**Распределение выводов ESP32:**

| ESP32 IO | Функция | LED | Способ подключения |
|---|---|---|---|
| IO17 | Global status (статус адаптера / ошибка / пейринг) | D3, синий | двухрезисторная pull-up схема (прямо) |
| IO2 | Port 1 status | D4, зелёный | через MOSFET Q1 (2N7000) |
| IO4 | Port 2 status | D5, зелёный | через MOSFET Q2 (2N7000) |

IO2/IO4/IO17 — все strapping-пины ESP32. Через MOSFET заведены только port-LED D4 (IO2) и D5 (IO4) — требование данной аппаратной ревизии BlueRetro, чтобы нагрузка LED не мешала загрузке; IO17 (D3) использует отдельную pull-up-схему без MOSFET (см. выше). Порты 3/4 (при расширении) — это IO12/IO15, но в режиме PlayStation они переназначаются под индикацию аналогового режима; для NES-режима неактуально.

**Логика поведения (подтверждена реальным тестом):**
- Питание, без ошибки → авто-пейринг: global-LED (IO17) **пульсирует** + LED первого доступного порта (IO2) **пульсирует**; второй порт (IO4) выключен.
- 1-й геймпад подключён → IO17 гаснет, порт 1 (IO2) **solid**.
- 2-й геймпад подключён → порт 2 (IO4) **solid**, IO17 остаётся выключенным.
- Отключение геймпада → его port-LED гаснет; при освобождении порта адаптер возвращается в пейринг (global + первый свободный порт снова пульсируют).

### Схема global-status LED IO17 (двухрезисторный вариант)

⚠️ Отличается от официальной однорезисторной схемы вики (R36 ≈ 65 Ом–1 кОм, LED прямо между узлом и GND). В данной сборке — **два резистора**, что улучшает поведение:

```
+3V3 --[R2 360R]--+-- IO17 (U1 pin 25)
                  |
                  +--[R3 150R]--[D3 anode >|< cathode]-- GND
```
IO17 подключён к узлу между R2 и R3 (со стороны анода LED), а не к GND-стороне.

**Роли резисторов:**
- **R2 = 360R** — pull-up 3.3V→IO17. Обеспечивает fail-safe (при high-Z LED тускло горит) и определяет паразитный сток в GPIO при LOW. На рабочую яркость **не влияет**.
- **R3 = 150R** — последовательный токоограничивающий резистор LED. Задаёт яркость в HIGH-PWM (пульсация/solid). Ограничивает ток при активном push-pull HIGH.

**Логика (fail-safe по умолчанию):**
- IO17 по умолчанию (не сконфигурирован, high-Z/вход) → R2 дотягивает узел к 3.3V → **LED тускло горит сам по себе**, без команды прошивки.
- Прошивка после успешного старта **явно переводит IO17 в выход LOW** → узел к 0V → **LED гаснет**.
- Смысл инверсии: если прошивка не загрузилась (краш до инициализации) — IO17 остаётся high-Z, LED **продолжает гореть** = индикация ошибки. В классической схеме такой сбой был бы неотличим от штатного «выключено».
- Пульсация/статус: прошивка через LEDC переключает IO17 в ШИМ (~200 мкс, скважность 0–20 %), создавая «дыхание». Подтверждено осциллографом.

### Схема port-status LED (IO2/IO4, через MOSFET)

```
+3V3 --[D4/D5 anode >|< cathode]--[R4/R5 510R]-- drain Q1/Q2
                                                 gate  -- IO2/IO4
                                                 source-- GND
```
При HIGH на IO2/IO4 → MOSFET открыт → LED горит. При закрытом MOSFET ток не течёт вообще — здесь **нет** проблемы «стока в GPIO» (в отличие от IO17), поэтому port-LED можно гонять на рабочем токе без оглядки на нагрузку GPIO.

### Итоговые номиналы и токи (измеренные Vf)

Vf измерены мультиметром-вольтметром на LED через 510R к 3.3V (высокий входной импеданс → честная рабочая точка): **синий Vf = 2.6 В @ ~1.4 мА, зелёный Vf = 2.4 В @ ~1.76 мА.**

| LED | Цвет | Vf | Цепь | Ток | Состояние |
|---|---|---|---|---|---|
| D3 (IO17) | синий | 2.6 В | R3 = 150R | ~4.0–4.5 мА | HIGH-PWM (пульсация/статус) |
| D3 (IO17) | синий | 2.6 В | R2 = 360R | ~9.2 мА | LOW — сток в GPIO (зависит только от R2) |
| D3 (IO17) | синий | 2.6 В | R2+R3 = 510R | ~1.37 мА | high-Z — fail-safe (ошибка старта) |
| D4/D5 (порты) | зелёный | 2.4 В | R4/R5 = 510R | ~1.76 мА | solid (порт подключён) |

**Баланс яркости:** port-LED зелёные работают при меньшем токе (~1.76 мА), чем синий статусный (~4.5 мА), но за счёт максимальной чувствительности глаза к зелёному (~555 нм) и слабой — к синему, визуально они сопоставимы. R4/R5 = 510R — при более низком номинале (150R) зелёный станет ярче синего, нарушая баланс.

**Визуальная проверка:** при одновременном свечении синего (IO17) и зелёного (порт 1) во время пейринга яркости сопоставимы. При необходимости R4/R5 можно снизить до ~330R (~2.7 мА) — но не ниже.

**Запас по напряжению (headroom):** у синего LED запас невелик (3.3 − 2.6 = 0.7 В), поэтому яркость чувствительна к просадкам 3.3V-шины — при 3.2 В ток в HIGH падает до ~4 мА, что остаётся в норме.

## Проверка сигналов осциллографом (подтверждено)

**CLOCK (GP14 → IO5/IO18):** период 80 мкс (≈12.5 кГц), скважность 50% (HIGH = LOW = 40 мкс), амплитуда 0V ↔ 3.3V, чистые фронты.

**LATCH (GP15 → IO32):** период повторения 1200 мкс (≈833 Гц), длительность импульса 40 мкс, амплитуда 0V ↔ 3.3V.

- Длительность импульса LATCH (40 мкс) равна одной фазе CLOCK — типично для фиксации параллельно загруженного состояния кнопок перед серией сдвиговых тактов.
- За один период LATCH укладывается 1200 / 80 = 15 полных тактов CLOCK — достаточно для вычитывания 8-битного регистра с запасом.
- Частота опроса (~833 Гц) заметно выше классической NES/Famicom (~60 Гц, синхронно с кадром) — предположительно осознанное решение прошивки Мурмулятора для снижения input lag.
- Амплитуда 0V/3.3V на обеих линиях подтверждает штатную работу топологии «один драйвер (Pico) — приёмники (ESP32)», без конфликта шины.

**DATA (IO19/IO22 → GP16/GP17):** при нажатии кнопок на геймпаде Xbox One (A, X, View, Menu, D-pad Up/Down/Left/Right на линии DATA наблюдается импульс **LOW (~0V) длительностью 80 мкс** — ровно один период CLOCK.
**Первая кнопка отдаётся без тактового импульса:** как только Мурмулятор подаёт сигнал LATCH (защёлка), микросхема мгновенно выставляет значение кнопки A на линию DATA (это 0-й бит). Следующие кнопки (X, View, Menu и т.д.) выдаются по очереди на каждый следующий тактовый импульс CLOCK.

- Протокол использует **инверсную логику**: LOW = кнопка нажата, HIGH (3.3V) = кнопка отпущена — штатное соглашение для NES/Dendy-совместимого сдвигового регистра.
- Длительность импульса (80 мкс) точно совпадает с периодом CLOCK — подтверждает, что каждый бит выставляется на DATA ровно на один такт сдвига, синхронно и без фазового сдвига.
- Соответствие «нажатая физическая кнопка Xbox → LOW-импульс в ожидаемом такте» подтверждает корректный маппинг BlueRetro (Xbox One HID → NES-биты) и правильное считывание Мурмулятором на стороне RP2040.

**Порядок бит DATA в сдвиговом регистре NES и соответствие Xbox One (подтверждено):**

| Такт | Бит | Кнопка Xbox One | Роль (NES-бит) |
|---|---|---|---|
| 1 | 0 | A | A |
| 2 | 1 | X | B |
| 3 | 2 | View | Select |
| 4 | 3 | Menu | Start |
| 5 | 4 | D-pad Up | Up |
| 6 | 5 | D-pad Down | Down |
| 7 | 6 | D-pad Left | Left |
| 8 | 7 | D-pad Right | Right |

Порядок бит **A, B, Select, Start, Up, Down, Left, Right** — это стандартный, канонический порядок выдачи бит в оригинальном NES-контроллере (тот же порядок, в котором консоль NES исторически считывала регистр 4021). Совпадение подтверждает, что BlueRetro в режиме `GamePad`/NES эмулирует классический протокол один в один, без изменения порядка бит, а Мурмулятор читает их в этом же порядке.

Проверка подтверждает как электрическую целостность сигналов CLOCK/LATCH, так и корректное фазовое согласование DATA относительно CLOCK — данные снимаются в правильный момент такта.

## Прошивка firmware (проверено, рабочий вариант)

**Версия прошивки:** `v25.04_hw1.zip` (архив с [GitHub Releases](https://github.com/darthcloud/BlueRetro/releases)) — используется HW1-спецификация (см. раздел "Аппаратная сборка BlueRetro").

**Файлы из архива:**
- `bootloader.bin`
- `partition-table.bin`
- `ota_data_initial.bin`
- `BlueRetro_hw1_nes.bin` (система-специфичная прошивка под NES)

**Команда прошивки (Windows, через PlatformIO Core):**

```
pio pkg exec -- esptool.py -p COM6 -b 460800 --before default_reset --after hard_reset --chip esp32 write_flash --flash_mode dio --flash_size detect --flash_freq 40m 0x1000 bootloader.bin 0x8000 partition-table.bin 0xD000 ota_data_initial.bin 0x10000 BlueRetro_hw1_nes.bin
```

Порт `COM6` — под конкретный экземпляр платы, уточнять в Диспетчере устройств Windows при каждой прошивке.

**Примечание:** при прямом вызове `python esptool.py ...` (не через `pio pkg exec`) может не хватать зависимостей esptool, так как системный Python не видит окружение, куда PlatformIO их устанавливал — команда через `pio pkg exec --` обходит эту проблему, используя корректное окружение автоматически.

**Full flash erase:**
```
pio pkg exec -- esptool.py -p COM6 --chip esp32 erase_flash
```

**Serial Monitor Debug:**
```
pio device monitor -p COM6 -b 921600
```

**Параметры SecureCRT Serial Monitor:**
```
Connection:
  Serial:
    Port: COM6
    Baud rate: 921600
Terminal:
  Emulation:
    Modes:
      [v] New line mode
```

### Первичная настройка после прошивки (BlueRetro Web Configurator)

После прошивки может потребоваться настройка через Web Config — в данном случае сборка заработала на дефолтных настройках, ниже приведена конфигурация для проверки/справки.

**Адрес:** [https://blueretro.io/](https://blueretro.io/)

⚠️ Конфигурация BlueRetro доступна только когда **ни один контроллер не подключён** — сделано специально, чтобы не отбирать эфирное время у геймпадов во время игры.

**Порядок действий:**
1. Открыть **"BlueRetro Advance config"**.
2. Нажать **[Connect BlueRetro]** — при необходимости повторять клик, пока не установится соединение.
3. Откроется всплывающее окно со списком Bluetooth-устройств — выбрать устройство BlueRetro и нажать **[Pair]**.
4. **Global Config:**
   - System: `NES`
   - Multitap: `None`
5. **Output Config:**
   - Output 1 → Mode: `GamePad`, Accessories: `None`
   - Output 2 → Mode: `GamePad`, Accessories: `None`
6. **[Save]**
